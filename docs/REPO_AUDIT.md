## 1. Executive Summary

This audit assesses the state of the **Kalaswar** repository prior to codebase restructuring. The goal is to evaluate what currently exists, identify Lovable boilerplate and scaffolded artifacts, verify what builds and runs in the local environment, and document structural gaps between the current implementation, the project `README.md`, and the product architecture masterplan (`docs/product/KALASWAR_MASTERPLAN.md`).

---

## 2. Inventory: What Exists Today

### 2.1 Codebase Layout
The repository was originally scaffolded as a fullstack TypeScript template (TanStack Start + Vite) using Lovable:
- **`frontend/`**: The bulk of the application code (~44 routes, 29+ domain libraries, UI component tree):
  - `frontend/src/routes/`: File-based routing for Customer Marketplace (`/`, `/explore`, `/artisans`, `/product/$id`), Customer Custom Orders (`/concierge`), Stories (`/stories/*`), Artisan Space (`/artisan-space`), SHG Coordinator Workroom (`/shg/*` with 11 sub-dashboards), B2B Sourcing Portal (`/b2b/*` with RFPs, quotes, sample tracking, buyer profile), and Auth (`/auth`, `/forgot-password`, `/reset-password`).
  - `frontend/src/routes/api/public/`: In-app SSR endpoints for voice handling (`stt.ts`, `tts.ts`, `assistant.ts`) invoking external AI gateways.
  - `frontend/src/lib/`: Core deterministic engines:
    - `makepossible.ts`: Deterministic feasibility evaluation against recorded craft capacity and skills.
    - `fairprice.ts`: Cost build-up calculator with time and material factors.
    - `i18n.tsx`: Single-dictionary multi-lingual support (English, Hindi, Marathi).
    - `data.ts`: Comprehensive TanStack Query options querying Supabase directly via the browser client under Row Level Security.
  - `frontend/src/test/`: 12 test suites verifying domain calculations (feasibility, pricing, B2B, earnings, demand, risk, artisan plans, localization).
- **`backend/`**: A misnomer in the current repo:
  - Contains **no Python or FastAPI code**.
  - Contains only Drizzle ORM artifacts: `drizzle.config.ts`, an empty `drizzle/schema.ts` (`// auto-generated and intentionally left blank`), and 13 SQL migration files (`backend/drizzle/migrations/0000_...` to `0012_...`).
  - `.env.example`: Lists environment variable templates.
- **`supabase/`**:
  - Contains only a single `config.toml` referencing `project_id = "attbdsvqjgjeeewcygod"`.
  - Migrations are not inside `supabase/migrations/` (they are in `backend/drizzle/migrations/`).
- **`docs/`**:
  - Rich documentation including `README.md`, `ROADMAP.md`, `REPOSITORY_STRUCTURE.md`, architecture diagrams, product audits, deployment guides, and the converted masterplan.
- **Root Tooling Configuration**:
  - `package.json`, `vite.config.ts`, `tsconfig.json`, `vitest.config.ts`, `eslint.config.js`, `components.json`, `bunfig.toml`, `bun.lock`.

## 3. Lovable Boilerplate & Coupling Analysis

The project originated from Lovable.dev's TanStack Start scaffolding. Key indicators and areas of coupling:
1. **Tooling & Build System**:
   - `vite.config.ts` imports `defineConfig` directly from `@lovable.dev/vite-tanstack-config`.
   - `package.json` contains `@lovable.dev/vite-tanstack-config: "2.26.5"`.
   - Root `bunfig.toml` and `bun.lock` were auto-generated by the cloud builder.
2. **AI & Error Reporting Integrations**:
   - `frontend/src/lib/lovable-error-reporting.ts`: Sends client errors to Lovable reporting endpoints.
   - `frontend/src/integrations/supabase/previewAuthStorage.ts`: Handles simulated preview auth tokens inside iframe environments.
   - `frontend/src/routes/api/public/assistant.ts`, `stt.ts`, `tts.ts`: Rely on `LOVABLE_API_KEY` and `https://ai.lovable.dev` as the AI Gateway for Whisper and LLM completions.
3. **Database Client Configuration**:
   - Direct browser-to-Supabase architecture without an intermediate API tier. All authorization currently relies on Supabase RLS.
4. **Annotations & Markers**:
   - `AGENTS.md` and `README.md` contain `<!-- LOVABLE:BEGIN -->` and `<!-- LOVABLE:END -->` banners cautioning against rebasing / force-pushing.

## 5. Architectural Gaps vs. README & Technical Masterplan

The product requirements outlined in `README.md` and the Technical Masterplan (`docs/product/KALASWAR_MASTERPLAN.md`) detail an enterprise operating system across 3 teammates (Web, WhatsApp/Backend, Blockchain). Comparison reveals significant gaps:

### 5.1 Backend Service (FastAPI)
- **Target Specification:** The masterplan defines a central **Kalaswar FastAPI Core Service** handling:
  - Whisper / Sarvam AI speech-to-text pipeline for vernacular voice notes.
  - Dynamic Cloudinary image pipeline (compression `f_auto,q_auto`, background removal, GI watermarking).
  - Multi-channel auto-publishing engine (ONDC protocol adapters, Kalaswar storefront).
  - Business actions and micro-factoring / escrow hooks.
- **Current Reality:** `backend/` has zero Python files. In-app voice routing is currently bundled directly into TanStack Start SSR routes (`frontend/src/routes/api/public/*`) calling Lovable's cloud gateway.

### 5.2 Primary Artisan Interface (WhatsApp Automation Bot)
- **Target Specification:** WhatsApp Business Bot (Meta Cloud API / Twilio / Gupshup) serving as the primary voice-first interface for semi-literate rural women artisans (3-step voice listing workflow, task guidance, DBT payout notifications).
- **Current Reality:** Only a web browser page (`/artisan-space`) exists, requiring a browser microphone and visual interface. The WhatsApp webhook receiver and conversational state machine do not exist.

### 5.3 Layer-2 Blockchain Provenance & Digital Product Passports (DPP)
- **Target Specification:**
  - Off-chain Merkle tree aggregation engine batching 500 production logs into a single root.
  - Daily Polygon/Solana smart contract commits (< $0.001/unit).
  - Public QR code scanner showing maker identity, GPS coordinates, and wage distribution.
  - Tokenized PO factoring for raw material advances.
- **Current Reality:** Zero Web3/Solidity/Ethers code exists. QR codes generated on the web app are standard UPI payment strings or catalog links, not cryptographic Merkle proof verifiers.

### 5.4 Database Organization & Supabase Migrations
- **Target Specification:** Supabase Postgres housing tables: `shg_clusters`, `artisans`, `products`, `dpp_passports`, `po_factoring` with fine-grained RLS.
- **Current Reality:**
  - Migrations exist in `backend/drizzle/migrations/` rather than standard `supabase/migrations/`.
  - Tables for `dpp_passports` and `po_factoring` are not yet created in the migrations.
  - Access is currently configured in demo mode with anonymous read/write policies to allow hackathon walkthroughs without mandatory authentication.

### 5.5 Mobile Application (Expo)
- **Target Specification:** Android dashboard for SHG coordinators and Community Resource Persons (CRPs) for offline-capable inventory tracking and village-level quality checks.
- **Current Reality:** No mobile repository exists yet.

## 6. Recommendations for Restructuring Plan

To enable the 3-person team (Web, WhatsApp/Backend, Blockchain) to work concurrently without merge conflicts:
1. **Preserve History with `git mv`**: Move the React application into `web/` alongside root Vite configurations.
2. **Establish `backend/` as FastAPI**: Scaffold a clean FastAPI service with an OpenAPI contract, Pydantic schemas, and endpoints for WhatsApp webhooks, AI pipelines, and business logic.
3. **Migrate Database to `supabase/`**: Move Drizzle SQL migrations into `supabase/migrations/` and establish `supabase/seed.sql` for reproducible local and cloud setups.
4. **Prepare `mobile/` Directory**: Reserve `mobile/` for future Expo scaffolding.
5. **Ensure Isolated Builds**: Verify that `web/` installs, tests, and builds independently from its new home.
